zt · Claude Code in Zellij · native Windows

Several sessions, one terminal

A guide to running more than one Claude Code session without losing track of them — written for someone who has never used Zellij and doesn't especially want to learn a multiplexer.

The problem this solves

Why one terminal is not enough, and why tabs alone don't fix it

Run Claude Code on one project and a single terminal is fine. Run it on three and the day becomes a hunt: which one finished, which is waiting for permission, which has been sitting idle for an hour because you forgot it. Nothing tells you. You go and look.

Terminal tabs don't fix that, because a tab can't tell you it needs something. What's needed is for each session to be able to raise its hand, and for something to be watching. That is what this is.

Everything below assumes one Zellij session holding one tab per project, with zt as the thing you type. A macro pad is optional and comes near the end — it is where the project started, but it is no longer the point of it.

The one idea worth understanding

Everything else follows from this

A macro pad can only send keystrokes to the window you are looking at. That is a hardware fact, not a limitation of the software. So a pad that types Enter can only answer a Claude Code prompt if Claude Code is the thing in front of you — which rather defeats the point of having a key for it.

Zellij dissolves that problem. It runs your shells inside itself, and it accepts instructions over a command line from anywhere on the machine. So instead of the pad typing at a window, the pad runs a command that says "put an Enter into that shell." The terminal window becomes a viewport onto something that exists independently of it.

That is the whole trick. Once input reaches the shell rather than the window, the terminal no longer needs to be focused — or even visible.

Zellij in ninety seconds

Four words you need; ignore the rest of the manual

Session A workspace that keeps running whether or not a window is showing it. Ours is called claude. Close the terminal and the session carries on; open one again and you're back where you were.
Tab One per project, named claude-<folder>. Each sits in its own directory with its own Claude Code instance.
Pane A split within a tab. You can ignore panes entirely — this rig doesn't need them.
Attach Pointing a terminal window at a running session. Detaching closes the window and leaves everything running.

Zellij is not a replacement for Windows Terminal, and you don't migrate to it. Windows Terminal is the window; Zellij runs inside it. Only the Claude session needs it.

The one gotcha

A detached session keeps running, but the pad cannot reach it. Every command silently does nothing and still reports success, so there is no error to find. Minimised is fine. Unfocused is fine. Closed is not.

If the pad ever seems dead, this is the first thing to check: zellij --session claude action list-clients. An empty list is the whole diagnosis.

The four keys

Two answer Claude; two move you between projects

Key 1 — Yes Sends Enter, accepting whatever option is highlighted. Ctrl+Shift+F13 · ~60 ms
Key 2 — No Sends Esc, rejecting the prompt. Ctrl+Shift+F14 · ~60 ms
Key 3 — Who needs me? Jumps to the session that has been waiting longest. Press again to walk to the next one. Ctrl+Shift+F15 · ~460 ms
Key 4 — Next project Cycles the Claude tabs, skipping any tab that is not a project. Ctrl+Shift+F16 · ~460 ms

Key 3 is the one that earns the hardware. Cycling tabs makes you hunt; key 3 makes the work raise its hand. It knows who is waiting because Claude Code fires a hook on every meaningful event, and that hook drops a small file naming the tab.

Why Enter and not "y". Claude Code's permission prompt is an arrow-key list, not a yes/no question — so Enter accepts the highlighted choice and typing a literal y does nothing at all.

What it looks like when it's working

The status bar, read at a glance

Every project shows a symbol and a colour along the bottom of the Zellij window. You are meant to read it peripherally and mostly not act on it:

vFinished — it has replied and is waiting for you
!Needs you — a permission prompt or a question
*Working — thinking, or you have just sent something
>Running a command
~Reading files
&Subagent running
.Idle

Green and red are the two that matter — both mean the machine has stopped and you are the bottleneck. That's your cue for key 3.

Optional

The bar needs the zjstatus plugin. Everything else — the flags, key 3, the jumping — works without it. If you'd rather not install a plugin, delete the default_tab_template block from the layout and carry on.

What you can actually do with it

The use cases that justify the setup

Answer a prompt without stopping what you're doing

Claude asks permission to run a command while you are reading something in a browser, on a second monitor, with the terminal minimised. Press key 1. Nothing flashes, nothing steals focus, no window comes forward. You carry on reading.

This is the case that made the rig worth building, and it is the one plain keyboard shortcuts cannot do at all.

Run several projects at once and be told which needs you

Give three projects a long task each and stop supervising them. When one finishes or gets stuck it raises its hand; key 3 takes you there. Press it again and you're at the next one, oldest first — so nothing sits ignored while you loop over the same tab.

Without this you either watch one session and waste the others, or you tab around hunting for the one that stopped.

Start something long and genuinely walk away

Kick off a refactor, close the laptop lid, come back later. The session keeps running; reattach and the scrollback and state are intact. Zellij also saves sessions to disk, so even an exited one can be resurrected with its tabs and directories.

Note the honest limit: while nothing is attached, the pad can't reach it. Reattach first, then the keys work again.

Add a project in one command, from the project

No config to edit, no layout file to touch:

cd F:\some\project
zt add .
zt start project

That registers the folder and opens a tab named after it, in the right directory, with Claude running. The name matters more than it looks: the hook derives the same identity from the directory Claude reports, so the flag file and the tab agree without anything being configured.

Most of the time you won't even type zt add — a Claude session started in a folder registers itself, and appears the next time you run zt.

Check who's waiting without looking at the screen

zt

  ID                   STATE        AGE       KIND     PATH
  ----------------------------------------------------------------------------
  zt                   WAITING      6m        claude   C:\code\zt
  api                  running      2h 14m    claude   C:\code\api
  web                  stopped      3d 4h     claude   C:\code\web

Useful from any other terminal, and it tells you what's idle as well as what's shouting.

Stop, restart, or clear out a project

zt stop api        # Ctrl+C it; the tab stays as a shell
zt restart api     # and resume the same Claude conversation
zt close api       # close the tab, keep the registration

Restart resumes rather than starting blank: the hook recorded the session id, so you get the conversation back. Stop deliberately leaves a prompt in the right directory rather than closing the tab — the project is still there, just idle.

Shut the machine down without losing your place

zt park            # stop everything, remember what was running
zt restore         # bring it back, resuming each conversation

There is deliberately no shutdown hook. Catching Windows on its way down gives you a few seconds and it can kill you anyway — so instead the loss is made cheap. Zellij resurrects its own tabs, and each Claude session id is recorded, so restoring picks the conversations back up.

zt park is optional. If the machine goes down without warning, zt restore still works: it falls back to the sessions that never got to exit cleanly, which is exactly the set worth reopening.

Use the same project list on more than one PC

Definitions live in git; where things actually are does not. A shared entry says root code, folder api, and each machine says where code is — C:\code on the desktop, C:\dev on the laptop. One config, no per-machine editing, and anything the current PC can't reach simply isn't offered.

Each machine only ever writes its own device file, so two PCs registering projects at the same time can't conflict.

Setting the pad up

One command, and one thing you must do by hand every time

The four keys are wired through PowerToys Keyboard Manager, which most Windows machines already run, so it costs no extra process:

zt pad install     # writes the four remaps
zt pad             # what is wired, and what is missing
zt pad probe       # which chords actually arrive

Then toggle Keyboard Manager off and on in PowerToys Settings. This is not optional and it is not obvious: its engine reads the config when it starts, never when the file changes. Until you toggle it, it keeps running whatever it loaded last — which is why the keys can go on working after the remaps are deleted, and why console windows can go on flashing after they have been set back to hidden. zt pad compares the engine's start time to the file and tells you when it is stale.

Two more things about that UI, both learned the hard way. Editing anything there silently downgrades our settings — it resets the windows to visible, so a console flashes on every key press; re-run zt pad install afterwards. And the per-entry toggle it shows is not stored anywhere: entries can read as switched off while working perfectly. Ignore it.

If a key does nothing, zt pad probe points all four at a logging command and tells you which ones arrive — separating "the chord never reached Windows" from "it arrived and the target failed", which otherwise look identical because both are silent.

In the Command Palette

The same rig, one keystroke away, with a dock band

An extension puts everything into PowerToys Command Palette — so you do not need a terminal open to see what is running:

cd cmdpal
.\pack.ps1         # build, sign, install — one command
WhereWhat
rootZellij workspaces, subtitled 3 registered, 2 running, 1 WAITING
rootaccept / reject a prompt, go to whoever's waiting, next tab, attach, sessions, park, restore
roottype a workspace name and it offers to jump straight there
dockthe workspace count, visible without summoning anything
per rowCtrl+S start · Ctrl+T stop · Ctrl+R restart · Ctrl+F flag · Ctrl+W close · Ctrl+D unregister

The dock band is the piece that replaced a planned tray icon. It sits in Command Palette's persistent strip and shows the count whether or not you are attached — which is exactly the case the status bar inside Zellij cannot cover, because it only exists while you are looking at it. zt dock pins it.

Why the pad still uses Keyboard Manager. Command Palette's own hotkeys are genuinely system-wide — proved by binding a chord Keyboard Manager knew nothing about and watching it fire. So the palette could drive the pad. It is not used, because the palette has crashed more than once while Keyboard Manager has not. The pad is the part that has to work; the palette is the part that makes it pleasant.

Sessions, and the level above tabs

Where stray things hide

Zellij has two levels, and conflating them wastes an afternoon. Sessions are separate servers, each with its own tabs and its own clients. Tabs live inside one session. Everything zt lists is tabs inside the session called claude, so they will never appear in zellij list-sessions.

The session level accumulates strays silently — an exited session is kept so it can be resurrected, and a mistyped command creates a whole new server named after a random animal. This machine quietly had two.

zt sessions                       # what exists, with tab and client counts
zt sessions kill <name> -Delete   # stop a stray and forget it

To wipe everything and start again, in this order — kill alone leaves them resurrectable:

zellij kill-all-sessions -y
zellij delete-all-sessions -y
zac

Claude Code's transcripts are on disk, not in the terminal, so claude --resume in a project folder picks a conversation back up afterwards. The workspace registry is untouched by any of it.

Things you might not realise are possible

Available now, or cheaply reachable

IdeaStatus
Answer a specific project's prompt regardless of which tab is focused, using --pane-id Possible today; not wired to a key
Long-press a key for a second action — accept, vs accept-and-don't-ask-again The pad's firmware supports it
Named keys (send-keys "Ctrl c") instead of raw byte values Confirmed available in Zellij 0.44.3
A Windows toast when a session needs you, for when the terminal isn't visible at all Straightforward; make it opt-in per project
Taskbar progress on the terminal button as a "needs you" signal Claude Code hooks expose the escape sequence for it
Drive it from a phone over SSH — approve prompts from another room Same commands; security needs thought
Build the tab list from your Windows Terminal profiles Done — -FromBookmarks

Two things are deliberately not possible, and are worth knowing so you don't chase them: a Zellij plugin cannot listen for the pad, because plugin key events only fire when the plugin's own pane is focused; and Windows' ControlSend cannot reach Windows Terminal, because it renders through DirectX and reads the focused-window keyboard path.

Inside Zellij itself, the keyboard is deliberately left alone: the config starts in locked mode so Zellij claims no shortcuts and Claude Code gets every key. Press Ctrl+g if you ever want Zellij's own keybindings.
